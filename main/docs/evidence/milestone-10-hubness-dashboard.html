이 흰 티셔츠는 왜 모든 검색에 걸려나올까

RAW 임베딩으로 만든 MVP에서 특정 상품이 관련 없는 검색에도 반복적으로 튀어나오는 현상을 발견했다. 실제 무신사 상품사진 2,160장으로 원인을 재현하고, detection/bbox 크롭이 그 원인을 실제로 해결하는지 정량적으로 검증했다.

Background

문제를 발견한 순서

  1. MVP: Marqo 임베딩 모델을 그대로 투입사진 업로드 → 유사 상품 Top-K 검색.
  2. 육안으로 봐도 안 유사한 결과가 섞여 나옴특정 쿼리와 무관해 보이는 상품이 계속 상위에 등장.
  3. 카탈로그 전체를 한 바퀴 돌려 Top-K 노출 빈도 집계몇몇 상품이 이상치로 유독 자주 검색됨을 확인.
  4. 그 상품들의 썸네일을 직접 확인일반 상품컷과 달리 의류 여러 개가 같이 보이거나 전신 착장샷.
  5. Detection + BBox 크롭 도입제품 영역만 잘라 임베딩 — 그런데 이 판단을 정량적으로 검증한 적은 없었음.

→ 이 리포트는 5번 판단을 사후에 정량 검증한다. 결론은 예상과 달랐다 (아래 "발견" 참고).

Experiment

Hubness 검증: RAW vs BBox

2,160장 전체를 서로에 대해 leave-one-out으로 검색 (각 이미지를 쿼리 삼아 나머지 2,159장 중 Top-10을 코사인 유사도로 계산). 각 상품이 "남의 Top-10"에 뽑힌 횟수를 집계 — 이 횟수가 비정상적으로 높은 상품이 hub다. BBox는 highest_confidence 정책(카테고리 무관, 최초 MVP 수준 fallback)으로 크롭.

Finding

가설은 틀렸다 — 그리고 그게 더 중요한 발견이다

원래 가설: "다중 아이템/전신샷 썸네일이 hub가 되고, bbox 크롭이 이를 줄여줄 것이다." 실제로는:

Hub의 정체는 messy 썸네일이 아니라 "무난한 디자인"이었다. 상위 hub 15개 중 14개가 단일 감지(clean shot)였고, 대부분 무지 화이트/베이직 티셔츠·후디였다. 전체 풀에서 messy 비율은 24.8%인데, 상위 1% hub 중 messy 비율은 9.1% — 오히려 평균보다 낮다.

즉 이 임베딩 공간에서 hub를 만드는 원인은 "사진에 뭐가 같이 찍혔는가"가 아니라 "옷 자체가 얼마나 무난하고 특징이 적은가"였다. 무지 화이트 티셔츠는 크롭을 해도 여전히 무지 화이트 티셔츠라서, bbox는 이 문제에 거의 영향을 주지 못한다 (Gini 0.5287 → 0.5267, 사실상 동일).

Cross-check

그럼 bbox 크롭 자체는 의미가 없었나 — 별개의 파일럿에서는 확실히 있었다

같은 프로젝트의 또 다른 실험(N=7 golden set, 3개 collection)에서는 category-aware bbox 정책이 실제로 검색 품질(NDCG@10)을 끌어올렸다. 단, 이번 hub 실험과는 다른 이유였다.

여기서 bbox가 이긴 이유는 hub 억제가 아니라 "엉뚱한 카테고리 선택 방지"였다 — 다중 아이템 사진에서 category 정보 없이 크롭하면(E1/E2) 아예 다른 종류의 옷(예: 니트 쿼리인데 청바지)을 잘라서 오히려 RAW보다 나빠졌고, category-aware 크롭(E3)만 이를 피했다. 즉 bbox의 진짜 효과는 "hub 억제"가 아니라 "카테고리 오검출 방지"였다 — 처음 가설과는 다른 메커니즘으로 유효했던 것.

Mitigation

그럼 뭘 해봤고, 뭐가 배포 가능했나

실제 UI가 카테고리별로 Top-K를 나눠 검색한다는 점에 착안해 두 가지를 테스트했다. 하나는 실패, 하나는 효과는 컸지만 실제 golden set으로 검증하니 관련도가 깎였다 — 배포 전에 반드시 확인해야 하는 이유가 정확히 여기서 드러났다.

Root Cause

재현성 문제를 파고들었더니 진짜 프로덕션 버그가 나왔다

Partial centering의 재현성 문제("같은 걸 두 번 돌렸는데 값이 다름")를 그냥 "노이즈"로 넘기지 않고 원인을 추적했다. 모델 forward pass 자체는 완벽히 결정적이었다 — 문제는 전처리 단계였다.

retrieval/models.py — 실제 코드

model, preprocess_val, _ = open_clip.create_model_and_transforms(model_name)
# open_clip은 (model, preprocess_train, preprocess_val) 순서로 반환한다.
# 변수명은 preprocess_val이지만 실제로는 preprocess_train이 들어갔고,
# 진짜 preprocess_val은 _ 로 버려졌다.

수정 후에는 α가 커질수록 NDCG가 단조적으로 하락한다 — "공짜로 hub도 줄이고 품질도 올리는" α는 존재하지 않는다. 이전에 찾았다고 생각한 α=0.4 스윗스팟은 전적으로 버그가 만든 노이즈였다.

Hub 분석의 핵심 결론(무난한 디자인이 hub 원인, bbox로 안 고쳐짐)은 버그 수정 후에도 그대로다 (Gini 0.529→0.530, 0.527→0.524 — 거의 변화 없음). 버그가 뒤집은 건 E0-E4 순위와 partial centering 권장안 두 가지였다.

Final Decision

N=11, 4개 카테고리 전부 — 처음으로 spec 기준을 통과한 golden set

dress_skirts 데이터가 없다는 게 이 프로젝트 전체의 마지막 구멍이었다. 또 다른 개인 프로젝트에서 원피스 25장/치마 14장을 찾았고, 그중 콜라주성 프로모션 배너(파일명에 옷 7개가 한꺼번에 나열된 것들)를 detection 개수로 자동 필터링해서 순수 단일 상품 사진 13장을 골라냈다.

Next

그래서 무엇을 고쳐야 하는가

  • 가장 먼저: transform 버그 수정을 그대로 배포한다. 다른 모든 결론과 무관하게, 같은 사진으로 검색해도 매번 다른 결과가 나오는 건 그 자체로 사용자에게 보이는 정확성 문제다.
  • Full mean-centering은 배포 안 함 — golden set 검증에서 NDCG가 떨어졌다. Partial centering도 재검증 결과 "공짜 스윗스팟"이 없는 걸로 확인됨 (α가 커질수록 NDCG가 단조 하락). Hub 억제와 relevance는 진짜 트레이드오프이고, 이건 제품 판단이 필요한 영역이다.
  • ADR-001: RAW로 최종 결정됨. N=11·4개 카테고리·결정적 재현으로 확정 — 더 이상 provisional이 아니다. final_config.yaml의 preprocessing도 raw로 반영함.
  • Hub 억제는 bbox로 해결될 문제가 아니다. 무난한 디자인이 원인이므로, 재순위화(re-ranking)로 고빈도 피검색 상품에 페널티를 주거나, 텍스트/속성 정보를 결합한 하이브리드 검색을 검토해야 한다.
  • "category-aware bbox가 카테고리 오검출을 막는다"는 메커니즘 자체는 여전히 유효하다 (버그 수정 후에도 E3/E4가 E1/E2를 확실히 이김) — 다만 그게 "hub 방지"는 아니라는 것과, RAW 대비 전체 우위는 재검증이 필요하다는 것 둘 다 정확히 구분해서 기록해야 한다.
  • N=7 골든셋은 여전히 파일럿 규모다. 이번 hub 분석(N=2,160)과 규모를 맞춘 진짜 retrieval 품질 검증(사람 다중 라벨링 + 4개 collection 전부)이 다음 단계.
  • "청바지 79.3% messy" 같은 카테고리별 편차를 감지 임계값에 반영할지 검토. 카테고리마다 전신샷 비율이 크게 달라, 단일 threshold가 최적이 아닐 수 있다.

Checklist

실무라면 여기서 더 확인했을 것들

  • 실 서비스 쿼리(중고 사용자가 실제로 올리는 사진)와 카탈로그(전문 상품컷)의 도메인 갭 — 이번 분석은 카탈로그 사진을 쿼리로도 썼기 때문에, 실제 도메인 갭에서 오는 hub 효과는 미포함.
  • Hub 상품이 실제 클릭/전환에 미치는 영향 — 자주 뽑힌다고 해서 항상 나쁜 건 아닐 수 있음 (진짜 인기 스타일일 가능성도 배제 못함). 오프라인 지표만으로는 구분 불가.
  • Detection threshold(0.3/0.4/0.5)별로 messy 판정 비율이 얼마나 민감하게 바뀌는지.
  • 카탈로그 규모가 커질 때(180장 → 수만 장) Gini 계수와 hub 개수가 어떻게 스케일되는지 — 지금 결과가 소규모 특유의 현상이 아님을 확인.
  • 재현성 — 같은 모델을 다른 랜덤시드/배치 순서로 다시 돌려도 hub 목록이 안정적인지.
